# 项目架构

更新日期：2026-08-03

## 目标

云海观象台需要同时处理四类工作：

1. 浏览器中的地图、探空图和交互操作；
2. 全球探空、地面站、气旋和模式资料获取；
3. 气象计算、质量控制、实况订正与出图；
4. 缓存、定时任务、监控和网站部署。

项目采用分阶段演进，不在第一版一次引入所有基础设施。

## 当前结构

```text
浏览器
  │
  ├── HTML / CSS / JavaScript
  │       │
  │       └── /api/v1/*
  │
FastAPI
  │
  ├── 页面和静态资源
  ├── 健康检查与模块状态
  ├── 探空实况与诊断 API
  ├── q-weather 逐小时与实时观测 API
  ├── ECMWF 单点与探空预报 API
  ├── 天气图配置和只读产品目录 API
  └── 站点目录、探空订正与导出 API

气象数据与诊断模块
  ├── meteostation/sounding/
  │       ├── 统一探空模型与热力诊断
  │       ├── Wyoming 适配器
  │       └── 原始 CSV 与元数据缓存
  └── meteostation/observation/
          ├── q-weather 逐小时序列标准化
          └── q-weather 实时状态解析

离线分析与制图工具
  ├── Basic_function/
  ├── MeteoMap/
  └── MeteoMap-ERA5average/
```

离线工具与网站请求链路隔离，用于 ERA5 研究、气候态计算和批量制图。

当前探空缓存路径按来源、年、月、日、站号和时次组织。缓存同时保存原始 CSV 和包含抓取时间、来源 URL、SHA-256、层数的 JSON 元数据。

### 采集与网页读取分离

探空资料不由网页请求即时抓取。`run_collector.py` 作为独立后台进程，负责新资料检查、保存和标准化；FastAPI 只读取本地归档，浏览器负责交互绘图与导出。

```text
Wyoming 轮询 / WIS 2.0 通知
             │
             ▼
       后台探空采集器
              │
              ▼
       原始资料与元数据
              ▼
       FastAPI 只读访问
              │
              ▼
     浏览器交互式 SVG / 数据表
```

生产环境中采集器只能运行一个有效实例；网站可以独立扩容。WIS 2.0 接入后，MQTT 事件替代大部分 Wyoming 轮询，但后续原始归档与浏览器出图方式不变。

V2.1.1 的地面实况页面按需查询 q-weather 逐小时资料，将各要素标准化为统一时序，再由网页绘制交互式 SVG 并导出 PNG。查询结果使用短时缓存，不写入气象产品归档。

## 目标结构

```text
外部资料源
  ├── Wyoming / WIS 2.0 探空
  ├── Aviation Weather METAR
  ├── q-weather 逐小时与实时
  ├── 热带气旋与高低压中心资料
  └── ECMWF
          │
          ▼
采集适配器 → 原始资料存档 → 解码与质量控制
                                  │
                                  ▼
                           统一气象数据模型
                            │             │
                            ▼             ▼
                    探空与订正算法     天气场分析任务
                            │             │
                            └──────┬──────┘
                                   ▼
                           FastAPI 数据接口
                                   │
                                   ▼
                           地图 / Skew-T / 导出
```

天气图当前链路进一步拆分为：

```text
ECMWF Open Data GRIB（上一 00/12 UTC 起报时次，+12 h）
  → 原始文件与请求元数据归档
  → cfgrib/eccodes 解码
  → 统一 WeatherGrid 字段
  ├─→ ERA5 1991—2020 同月 500 hPa 高度常值场 → 高度距平
  → 分层 NaN 感知高斯平滑（风羽不平滑）
  ├─→ 地面 TFP + 锋生/形变/辐合/温度平流 → 冷锋、暖锋、静止锋
  ├─→ 500 hPa 高度曲率 + 零经向地转风线 → 槽轴、脊轴
  ├─→ 实际 Matplotlib 图框边界 → 产品元数据 → 浏览器探空站精确配准
  ├─→ NRL 热带气旋 + 分层客观 H/L 中心 + 88 个 Wyoming 中国探空站叠加
  ├─→ 本地天地图省界与南海诸岛小图开发预览（data/previews，禁止发布）
  └─→ 天地图 vec/cva/ibo 瓦片缓存与经纬网格重采样
          → 城市水系、境界 + 观测订正（待令牌与送审）
          → 正式产品目录（data/products）
```

开发预览和正式产品使用不同目录及 API；本地 `中国_省.geojson` 只作为来源、哈希可追溯的天地图边界层，避免在专题地图审核完成前误发布开发成图。

## 设计原则

### 数据源可替换

浏览器与科学算法不直接依赖 q-weather、Wyoming 等外部响应格式。各资料源先转换为统一模型，再进入质量控制、诊断和绘图流程。

### 原始资料可追溯

系统保留原始报文或原始响应的哈希、抓取时间和来源。处理后的每个关键字段保留来源、质量标记和是否估算。

### 科学计算与页面分离

阈值、层结识别、气块订正和导出图形属于独立的 Python 领域模块，不写在 HTTP 路由或浏览器事件代码中。

### 快速产品与最终产品分离

00/12 UTC 资料到齐前可以生成快速版本；资料补全、质量控制和订正完成后生成最终版本。页面必须显示产品状态和资料截止时间。

### 历史回溯只读归档

日期选择器读取已经生成并保存的分析产品。普通网页访问不得因为用户选择历史日期而重新抓取外部资料或重新分析绘图。

后台定时任务负责获取新资料并写入原始归档。原始观测与来源元数据长期保留；交互探空不建立服务器端 PNG、JSON 示例目录，由浏览器从归档数据统一绘制与导出。未来如需保留正式发布版本，再将经过版本管理的产品写入独立对象存储。

### 地图合规优先

中国主页地图选用天地图权威地图服务，不自行拼制中国国界。底图服务来源审图号与本站气象专题地图审图号分开记录；只有服务令牌、专题地图送审和发布审图号全部落实后，正式产品开关才能启用。

## 预期部署形态

首版可以在一台服务器上运行：

- 一个 FastAPI 网站进程；
- 一个定时采集与分析任务进程；
- 文件缓存或轻量数据库；
- Nginx/Caddy 负责 HTTPS 和反向代理。

只有在任务量和访问量确有需要时，再拆分消息队列、对象存储和独立前端服务。
